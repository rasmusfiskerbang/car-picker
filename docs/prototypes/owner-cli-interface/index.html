Which owner CLI feels honest under pressure?

This demo compares three exact command interfaces for the Provider Registry, Catalogue, and Catalogue Site. Drive the awkward cases and watch the three durable states separately: changing provider state does not rewrite the dated Dataset, a failed refresh preserves that Dataset, and a valid older site is not corrupt merely because a newer Dataset exists.

PROTOTYPE

Nothing here contacts providers or writes repository data. The terminal and workspace are simulated in memory so the interface can be judged before the clean-room rewrite begins.

  • Noun-first commands
  • One complete all-provider refresh
  • Atomic replacements
  • No source URL flags
  • No pipeline commands
  • No catch-all validation
  • Loopback serving by default

Working recommendation

Use explicit verbs inside stable domain nouns

The defaults-first interface is the strongest starting point. It keeps the CLI a shallow adapter while making help, routine operation, and recovery legible without a manual. Human output is the default; one stable --json switch supports automation without turning the CLI into a raw storage editor.

  • Keep one explicit --workspace; reject per-artifact path flags.
  • Use provider inspect/set, not lifecycle verbs that imply a transition graph.
  • Use catalogue refresh/inspect; do not expose collection or admission steps.
  • Use site build/serve; neither command refreshes implicitly.
  • Use exit 0/1/2/70/130 plus stable diagnostic codes, not many script-specific exits.
  • Default serving to 127.0.0.1:4173; LAN exposure is explicit.
