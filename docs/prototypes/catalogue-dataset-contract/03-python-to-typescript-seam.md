# PROTOTYPE — Python-to-TypeScript seam

The seam has one source model, one generated schema constant, one generated type from that same schema, and one runtime parser. The browser never imports handwritten domain interfaces.

> **Accepted 2 August 2026.** Retain the Zod 4 `fromJSONSchema()` plus `json-schema-to-typescript` pipeline and one isolated typed bridge, guarded by parity tests. See [CatalogueDataset Python-to-TypeScript contract toolchain research](../../research/catalogue-dataset-typescript-contract-toolchain.md) for the verified library comparison and rejected alternatives.

## Compatibility finding

The most attractive pipeline is not available with the installed stack. Zod 4.4.3 declares:

```ts
function fromJSONSchema(
  schema: JSONSchema.JSONSchema | boolean,
  params?: FromJSONSchemaParams,
): ZodType;
```

The returned `ZodType` has no static output parameter derived from the input schema. Consequently, this compiles but `CatalogueDataset` is effectively unknown rather than the Dataset shape:

```ts
const CatalogueDatasetSchema = z.fromJSONSchema(catalogueDatasetJsonSchema);
type CatalogueDataset = z.infer<typeof CatalogueDatasetSchema>;
```

The converter is also marked semi-experimental in the installed Zod source. The contract should not claim stronger static inference than the dependency provides.

The recommended v1 compromise is to generate a TypeScript type and the runtime Zod validator from the same Pydantic JSON Schema, isolate their connection in one audited cast, and export `z.infer` from the bridged validator. This keeps one contract authority and no handwritten domain interface while retaining the map's chosen runtime converter.

## Ownership

                                    one isolated typed bridge
                                                       │

There is one generated TypeScript type beside the generated schema constant. Both are disposable outputs of the same JSON Schema. There is no handwritten Dataset interface and no presentation model.

## Python source of truth

Illustrative shape, not implementation code:

```py
class CatalogueDataset(CatalogueModel):
    schema_version: Literal["catalogue-dataset/v1"]
    generated_at: AwareDatetime
    providers: tuple[ProviderRecord, ...]
    offers: tuple[CatalogueOffer, ...]
    quarantined_candidates: tuple[QuarantinedCandidate, ...]


def catalogue_dataset_json_schema() -> dict[str, JsonValue]:
    return CatalogueDataset.model_json_schema(
        mode="serialization",
        by_alias=True,
        ref_template="#/$defs/{model}",
    )
```

The shared Pydantic base model:

- generates camelCase serialization aliases;
- uses strict validation and `extra="forbid"`;
- serializes finite float DKK values as JSON numbers and rounds materialized monetary results to two decimal places;
- emits closed discriminated unions;
- canonicalizes UTC timestamps before serialization.

Whole-Dataset invariants remain Pydantic behavior. JSON Schema guards the JSON shape in the browser; it is not expected to reimplement cross-record arithmetic.

## Generated schema constant

`CatalogueSite.build()` generates three equivalent outputs from the same schema dictionary:

1. `catalogue-dataset.schema.json`, copied into the completed site for inspection and artifact verification.
2. `catalogue-dataset.schema.generated.ts`, used only as a frontend build input:

```ts
// Generated from Python CatalogueDataset serialization schema. Do not edit.
export const catalogueDatasetJsonSchema = {
  // exact generated schema object
} as const;
```

3. `catalogue-dataset.generated.ts`, generated by the repository's existing `json-schema-to-typescript` tool from that same schema and used only for its static `CatalogueDataset` type.

Generating a TypeScript constant rather than importing ordinary JSON preserves the exact schema value passed to `z.fromJSONSchema()`. Both generated TypeScript files are disposable build output and do not belong in Git history. The completed JavaScript bundle embeds the schema constant and validator; generated types disappear at compile time.

## Browser interface

The frontend's single data module is approximately:

```ts
import { z } from "zod";

import { catalogueDatasetJsonSchema } from "./generated/catalogue-dataset.schema.generated";
import type { CatalogueDataset as GeneratedCatalogueDataset } from "./generated/catalogue-dataset.generated";

const convertedCatalogueDatasetSchema = z.fromJSONSchema(catalogueDatasetJsonSchema);

// The only type assertion at the data seam. Both sides are generated from the
// same Pydantic serialization schema and checked together during the build.
export const CatalogueDatasetSchema =
  convertedCatalogueDatasetSchema as z.ZodType<GeneratedCatalogueDataset>;

export type CatalogueDataset = z.infer<typeof CatalogueDatasetSchema>;

export const parseCatalogueDataset = (input: unknown): CatalogueDataset =>
  CatalogueDatasetSchema.parse(input);
```

Callers import `CatalogueDataset` and `parseCatalogueDataset` from this module, never generated internals. The application fetches `catalogue-dataset.json` and parses it once at startup. A parse failure replaces the application with one explicit invalid-artifact state; pages and feature modules receive only parsed data.

The cast is a real compromise, not decorative boilerplate. Its safety comes from keeping both generators on the same input, constraining the Pydantic schema to the JSON Schema features both tools support, and exercising representative union branches through both Python and Zod during the site build. If the owner rejects any cast at this seam, the alternative is to replace `z.fromJSONSchema()` with a build-time JSON-Schema-to-Zod-source generator and infer directly from the generated Zod code. That removes the bridge but changes the already chosen toolchain and adds another converter to evaluate.

Frontend helpers may format DKK, map enums and fact states to Danish labels, derive search text, and render arithmetic from validated inputs. They do not define a second Dataset type or transform the Dataset into a durable presentation model.

## `CatalogueSite.build()` flow

1. Open the active Dataset through `Catalogue.current()` and validate it with the authoritative Pydantic model, including recomputation of all materialized results.
2. Generate the serialization-mode JSON Schema from that same model.
3. Stage the static site.
4. Copy the validated Dataset bytes unchanged to `catalogue-dataset.json` in staging.
5. Write the schema JSON, generated TypeScript constant, and generated TypeScript type from the same canonical schema dictionary.
6. Parse the fixed contract examples with both Pydantic and the converted Zod validator, then type-check the frontend.
7. Build the frontend bundle.
8. Verify that staging contains the exact Dataset, matching schema artifact, frontend assets, and no forbidden files or keys.
9. Atomically replace the completed site artifact.

`CatalogueSite.open()` repeats artifact-level integrity checks but does not reject an older valid generation merely because a newer Dataset exists.

## Versioning rules

`schemaVersion` is a closed document-family discriminator, not package SemVer.

- `catalogue-dataset/v1` accepts exactly one JSON shape. Unknown fields are rejected.
- Any field addition, removal, rename, type change, enum change, altered optionality, or changed semantic invariant creates `catalogue-dataset/v2`.
- Formatting changes that leave the parsed value and schema unchanged do not create a version.
- The clean-room application supports only its current version. It has no historical migration chain because no historical Dataset is retained.
- A version change is implemented atomically: Pydantic model, materialization validators, schema constant, browser code, fixed fixture, and completed-site checks move together.
- The version literal is the first error reported when a browser or owner command opens an incompatible artifact.

This intentionally treats additive JSON changes as breaking. Strictness prevents an older browser from silently ignoring a new fact that might change comparison meaning.

## Validation split

| Concern | Owner | Checked when |
| --- | --- | --- |
| JSON field shape and discriminators | Pydantic model / generated JSON Schema | Refresh, site build, browser startup |
| Static TypeScript shape | Generated from the Pydantic JSON Schema | Frontend build |
| Cross-record identities and active-provider references | `CatalogueDataset` whole-model validator | Refresh and site build |
| Derived arithmetic and reconciliation | `CatalogueDataset` whole-model validator | Refresh and site build |
| Static artifact completeness | `CatalogueSite` | Build and open |
| Danish labels and formatting | Frontend feature modules | Browser rendering |
| Provider retrieval and evidence extraction | Provider Adapters | Catalogue Refresh |

Validation stays at the seam owning each risk. There is no catch-all validator module or release-check command.

## Failure behavior

- A Provider Adapter structural failure prevents Dataset construction and leaves the active Dataset untouched.
- A candidate-local admission failure becomes a Quarantined Candidate when it has stable identity and supporting evidence.
- A materialized-result mismatch rejects the replacement Dataset rather than trusting either stored or recalculated output.
- A site-build schema-generation or frontend-build failure leaves the previous completed site untouched.
- Browser parse failure shows no catalogue data. It does not fall back to unchecked JSON or attempt an in-browser migration.

## Contract checks worth carrying into implementation

These describe public behavior and belong at the owner-facing seams, not as a test for every Pydantic class:

- A refresh cannot persist a Dataset whose materialized results disagree with its normalized inputs.
- A site build packages the active Dataset without projection or field loss.
- The schema artifact and embedded Zod schema originate from the same Pydantic serialization schema.
- Representative known-fact, unavailable-fact, available-result, unavailable-result, reconciliation, Provider Registry, and quarantine branches parse in both Pydantic and Zod during the build.
- The completed browser rejects a deliberately incompatible Dataset at startup.
- Grepping a completed Dataset for forbidden evidence and operational keys finds none outside Quarantined Candidate evidence.
- A schema-version change fails loudly until backend, artifact, and browser move together.
